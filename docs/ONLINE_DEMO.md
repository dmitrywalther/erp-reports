# Конфигурация бесплатного демо

Для публичного демо подготовлен один Docker-сервис Render Free: R/Shiny и
локальный PostgreSQL работают в одном контейнере. База содержит только
синтетические данные и пересоздаётся при запуске. Управляемая Render Postgres
и постоянный диск для этой конфигурации не нужны.

Конфигурация находится в [render.yaml](../render.yaml), образ — в
[demo/online/Dockerfile](../demo/online/Dockerfile). **Публичный стенд не создан:**
проверена локальная сборка и работа контейнера с лимитами бесплатного тарифа.
Инструкция ниже сохранена для возможного последующего развёртывания.

## Если понадобится развёртывание

1. Создайте аккаунт Render и подключите публичный репозиторий проекта. Можно
   использовать GitHub-интеграцию или указать публичный Git URL вручную.
2. Создайте Blueprint из `render.yaml` либо Web Service с параметрами ниже.
   Проверьте, что выбран **Free**, без дополнительных БД и дисков.
3. Дождитесь завершения сборки и успешной проверки готовности. Откройте
   назначенный Render HTTPS-адрес и войдите как **`demo` / `demo`**.
4. Проверьте основные отчёты и скачивание Excel. После засыпания сервиса
   повторно откройте адрес и проверьте, что демо восстанавливается.
5. Добавьте проверенный адрес в README и резюме. Публиковать адрес до успешной
   проверки входа и отчётов не следует.

| Параметр | Значение |
|---|---|
| Runtime | Docker |
| Dockerfile Path | `./demo/online/Dockerfile` |
| Docker Build Context | `.` |
| Compute | Free |
| Переменная окружения | `ERP_REPORTS_DEMO=true` |
| Автоматический deploy | Отключён в `render.yaml`; обновление запускается вручную |
| Health Check Path | `/health/ready` |

Сервис получает адрес `*.onrender.com` с TLS. GitHub-интеграция позволяет
подключать автоматические обновления; при использовании публичного Git URL
без интеграции обновления запускаются вручную. Инструкция Render использует
бесплатные ресурсы и не требует оплаты. [Web Services](https://render.com/docs/web-services),
[Git provider](https://render.com/docs/git-provider),
[первое развёртывание](https://render.com/docs/your-first-deploy).

## Как устроен запуск

Стартовый сценарий — [entrypoint.sh](../demo/online/entrypoint.sh),
запуск Shiny — [run_app.R](../demo/online/run_app.R). Контейнер запускается
от отдельного непривилегированного пользователя. Shiny принимает соединения
на `0.0.0.0` и порту из `PORT`, который передаёт Render. PostgreSQL не должен
быть доступен через публичный порт сервиса.

Сценарий создаёт отдельный временный кластер PostgreSQL и задаёт четыре
подключения приложения к `127.0.0.1:5432`, БД `erp_demo`. Внешние настройки БД
перезаписываются. После генерации приложение использует роль с правом SELECT
и read-only транзакциями; SQL-запрос ограничен 30 секундами. Проверка
`/health/ready` появляется после проверки наполнения и прав подключения.

Хранилище контейнера временное. После остановки, перезапуска или нового deploy
содержимое БД создаётся заново из [схемы](../demo/schema.sql) и
[генератора](../demo/seed_demo.R). Даты генератора привязаны к запуску, поэтому
числа между перезапусками могут меняться. Фильтры и вычисленные таблицы
приложения относятся к сессии посетителя.

Загрузка пользовательских Excel отключена в интерфейсе и серверных обработчиках
онлайн-режима; импорт доступен локально. Дополнительно установлен лимит запроса
Shiny в 1 MiB. Выгрузки Excel создаются из выбранных синтетических данных.

Это отдельная конфигурация от локального Docker Compose из README. Не
подключайте её к рабочей БД: онлайн-демо рассчитано на воспроизводимую синтетику,
а не на сохранение пользовательских данных.

## Ограничения бесплатного сервиса

Условия проверены по официальной документации **1 ноября 2026 года**.

- Free предоставляет **512 MB RAM и 0,1 CPU**. Сборка использует отдельные
  ресурсы: Starter pipeline — 2 CPU и 8 GB RAM; это не память работающего
  приложения. [Compute plans](https://render.com/docs/compute-plans),
  [Build Pipeline](https://render.com/docs/build-pipeline).
- Через 15 минут без входящих HTTP-запросов или WebSocket-сообщений сервис
  засыпает. Следующий запрос запускает его снова; ориентир платформы — около
  минуты, к которой добавляются инициализация БД и запуск R. Render может
  перезапустить Free-сервис в любой момент. [Free](https://render.com/docs/free).
- Workspace получает 750 Free instance-hours в месяц. Сон не расходует эти
  часы. Квота сборки Hobby — 500 минут в месяц; одна сборка ограничена
  120 минутами и 16 GB диска. [Free](https://render.com/docs/free),
  [Build Pipeline](https://render.com/docs/build-pipeline).
- При превышении квот трафика или сборки и отсутствии платёжного метода
  Render приостанавливает соответствующие ресурсы. Если карта добавлена,
  возможны доплаты за превышение; для сборок предусмотрен spending limit.
  Бесплатный compute сам по себе не ограничивает все возможные расходы
  аккаунта. [Billing FAQ](https://render.com/docs/faq).
- Управляемая бесплатная Render Postgres истекает через 30 дней. В этой
  конфигурации она **не используется**: локальная БД временная, без резервного
  копирования и сохранения между перезапусками. [Free](https://render.com/docs/free).

Render поддерживает публичные WebSocket-соединения без фиксированной
максимальной длительности. Перезапуск сервиса прерывает текущие сессии;
посетителю понадобится открыть приложение заново.
[WebSockets](https://render.com/docs/websocket).

На готовность нового экземпляра выделяется 15 минут. HTTP healthcheck должен
вернуть 2xx/3xx за 5 секунд; непрерывные ошибки в течение 60 секунд у работающего
экземпляра приводят к перезапуску. Поэтому проверка тяжёлых отчётов и памяти
нужна до публикации ссылки. [Health Checks](https://render.com/docs/health-checks).

## Проверки

Тест [test_session_isolation.R](../demo/test_session_isolation.R) проверяет
раздельное состояние отчётов в двух сессиях. Контракт запуска проверяет
[test_online_runtime.R](../demo/test_online_runtime.R). Общие команды проверок
приведены в [README](../README.md#проверки).

Для 70 загрузчиков предусмотрен отдельный режим
`Rscript --vanilla demo/test_helpers.R --online`. Он работает только внутри
готового контейнера `/app`, от непривилегированного пользователя и с окружением
действующего процесса приложения. Обычный `docker exec` не наследует
сгенерированные при запуске параметры подключения. Сценарий проверяет
внутренний адрес БД, роль и read-only режим; без `--online` сохраняется обычная
локальная проверка `127.0.0.1:5433`.

### Результаты локальной проверки, 1 ноября 2026 года

Образ собран из публичного экспорта, включая установку R-пакетов и загрузку
`global.R` от пользователя контейнера. При сборке исправлена недостающая
системная зависимость `libglpk40`; для архивных бинарных пакетов R задан
совместимый HTTP User-Agent.

| Проверка | Результат |
|---|---|
| Регрессионные сценарии в Linux | 11/11 пройдены |
| Загрузчики в Linux | 70/70, ошибок и бесконечных значений нет; 2 корректно пустых результата |
| Права приложения | SELECT работает; INSERT, создание таблиц, схем и временных таблиц запрещены даже при отключении read-only транзакции |
| Bootstrap-пользователь БД | Вход по TCP и Unix socket запрещён после генерации |
| Два посетителя | Разные периоды дают независимые таблицы и суммы; изменение второго не меняет первый отчёт |
| Отчёты в браузере при 512 MiB / 0,1 CPU | Оборот, KPI, НДЗ/ПДЗ, индикатив цен, спот и скачивание страхового Excel проверены |
| Финальный образ при 512 MiB / 0,1 CPU | Холодный старт 258,68 с до HTTP 200, память после старта 337,9 MiB, OOM нет |
| Остановка через SIGTERM | 0,89 с; exit 143, временный кластер удалён |
| Повторный запуск без ограничения CPU | 20,31 с до HTTP 200; новая синтетическая база и повторная проверка прав |

Обычное приложение проверялось с **512 MiB памяти, без swap и 0,1 CPU**.
Первый холодный запуск занял **220 секунд** до `/health/ready`, повторный
контрольный запуск финального образа — **258,68 секунды**. После просмотра
отчётов и загрузки второй сессии наблюдалось около 379–445 MiB рабочей памяти;
с двумя заполненными отчётами — 403 MiB. Завершений из-за нехватки памяти не было
(`oom=0`, `oom_kill=0`). Память с файловым кешем доходила до установленного
лимита, поэтому это проверка двух посетителей, а не гарантия высокой нагрузки.
Выгрузка Excel при ограничении CPU занимала около 38 секунд. Просмотр основных
отчётов и двух сессий выполнялся до последнего исправления форматирования дней
НДЗ; финальные НДЗ дополнительно просмотрены в тестовом контейнере после исправления.

Полный набор R-тестов выполнялся в отдельном контейнере с 1 GiB памяти без
лимита CPU: дополнительные тестовые процессы запускаются одновременно с
приложением. Проверка остановки и повторного запуска в таблице относится
к этому контейнеру. Windows-проверки также пройдены: 11 сценариев и 70 загрузчиков.

При проверке исправлены общее состояние отчётов между сессиями и обработка
пропусков в днях НДЗ. В онлайн-режиме отключены пользовательские Excel-загрузки
и фоновый опрос неизменной синтетики; ожидание внешнего OSRM ограничено
5 секундами с переходом к прямой линии при ошибке.

Команды локальной сборки и запуска с ограничениями приведены в
[README](../README.md#docker-автономное-демо). Реальная инфраструктура Render,
пробуждение после облачного сна и публичный HTTPS/WebSocket не проверялись.
Старый `demo/docker-compose.yml` в этот прогон не входил.

Календарь, внешние карты, сценарии с пользовательским Excel и остальные
границы функциональности описаны в [README](../README.md#границы-демо).
Правила состава и проверки публичной копии — в
[PUBLICATION.md](PUBLICATION.md).
